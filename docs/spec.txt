Key formulas Match score matchScore = (skillsMatch * 0.40 + experienceMatch * 0.25 + educationMatch * 0.10 + projectRelevance * 0.15 + titleMatch * 0.10) * 100 Realness score realnessScore = (sourceReliability * 0.35 + freshness * 0.30 + specificity * 0.20 + companySignals * 0.15) * 100 Dedup hash dedupHash = SHA256(normalize(company) + normalize(title) + normalize(location)) 9. Caching strategies Karmio uses a multi-layer caching approach to minimize database queries, reduce API latency, and keep costs low. We use Vercel's built-in edge cache for static assets and API responses, plus in-memory caching for frequently accessed data. Layer 1: Browser cache (client-side) React Query (TanStack Query) handles all client-side caching with stale-while-revalidate patterns: Data type Stale time Cache time Refetch strategy User profile 5 minutes 30 minutes On window focus Job feed 2 minutes 10 minutes On window focus + interval 2min Today's matches 5 minutes 30 minutes On window focus Single job detail 10 minutes 60 minutes On demand Resume recipes 30 minutes 2 hours On demand Application list 1 minute 10 minutes On mutation Analytics data 5 minutes 30 minutes On window focus Contacts list 5 minutes 30 minutes On mutation Follow-ups 1 minute 5 minutes On window focus Subscription status 15 minutes 60 minutes On window focus // hooks/useJobs.ts export function useJobFeed(filters: IJobFilters) { return useQuery({ queryKey: ['jobs', 'feed', filters], queryFn: () => fetchAPI('/api/jobs', { params: filters }), staleTime: 2 * 60 * 1000, // 2 minutes gcTime: 10 * 60 * 1000, // 10 minutes garbage collect refetchOnWindowFocus: true, refetchInterval: 2 * 60 * 1000, // Poll every 2 min }); } Layer 2: API route cache (server-side) Next.js API routes use cache headers and Vercel edge cache for responses that do not change frequently: Endpoint Cache strategy TTL Invalidation trigger GET /api/jobs Edge cache + stale-while-revalidate 60 seconds New jobs fetched by cron GET /api/jobs/today Edge cache per user 5 minutes New cron run GET /api/jobs/[id] Edge cache shared 10 minutes Job updated/deactivated GET /api/analytics/overview Per-user cache 5 minutes Application status change GET /api/analytics/weekly Per-user cache 15 minutes End of day GET /api/profile Per-user cache Until mutation Profile update GET /api/subscription/status Per-user cache 15 minutes Stripe webhook // API route with cache headers export async function GET(req: NextRequest) { const data = await fetchJobs(filters); return NextResponse.json({ success: true, data }, { headers: { 'Cache-Control': 'public, s-maxage=60, stale-while-revalidate=120', 'CDN-Cache-Control': 'public, max-age=60', } }); } Layer 3: Database query cache (Supabase) For expensive queries (analytics aggregations, match score calculations across many jobs), we use materialized results stored in dedicated cache tables: user_job_matches: Pre-calculated match scores between users and active jobs. Recalculated when user updates profile or new jobs are ingested. Prevents real-time score computation on every feed load. daily_match_cache: Today's curated matches per user. Generated once at 7am user timezone by a cron function. Served directly without recalculation throughout the day. analytics_cache: Weekly aggregations (total applied, callback rate, match scores) computed nightly. Dashboard reads from cache, not from raw application table scans. Cache invalidation rules Profile update: invalidate user_job_matches for that user, recalculate within 60 seconds. New job batch: recalculate affected user_job_matches asynchronously. Application status change: invalidate analytics_cache for that user. Subscription change: invalidate subscription status cache immediately via Stripe webhook. 10. Database optimization Indexing strategy Indexes are created on columns used in WHERE clauses, JOIN conditions, and ORDER BY. We use partial indexes where possible to reduce index size. -- Job search indexes (most queried table) CREATE INDEX idx_jobs_active ON job_postings (is_active) WHERE is_active = true; CREATE INDEX idx_jobs_country ON job_postings (country) WHERE is_active = true; CREATE INDEX idx_jobs_first_seen ON job_postings (first_seen_at DESC) WHERE is_active = true; CREATE INDEX idx_jobs_realness ON job_postings (realness_score DESC) WHERE is_active = true; CREATE INDEX idx_jobs_dedup ON job_postings (dedup_hash); CREATE INDEX idx_jobs_title_trgm ON job_postings USING gin (title gin_trgm_ops); CREATE INDEX idx_jobs_sponsor ON job_postings (sponsorship_status) WHERE is_active = true; -- Application indexes CREATE INDEX idx_apps_user ON applications (user_id, created_at DESC); CREATE INDEX idx_apps_status ON applications (user_id, status); CREATE INDEX idx_apps_job ON applications (job_id); -- Follow-up indexes CREATE INDEX idx_followups_due ON follow_ups (user_id, due_date) WHERE is_completed = false; -- Weekly usage (checked on every tier-gated request) CREATE UNIQUE INDEX idx_usage_user_week ON weekly_usage (user_id, week_start); Query optimization patterns Pagination: Cursor-based pagination for job feeds (using first_seen_at + id as cursor), not OFFSET. OFFSET gets slower as you page deeper. Cursor stays O(1). Select only needed columns: Job list queries select only id, company_name, title, location, match_score, first_seen_at, sponsorship_status. Full description_raw and description_parsed loaded only when user clicks into a job detail. Batch inserts for job ingestion: Cron worker inserts new jobs in batches of 50 using INSERT ... ON CONFLICT (dedup_hash) DO UPDATE SET last_seen_at = NOW(). Single query handles both new and existing jobs. Connection pooling: Supabase includes PgBouncer for connection pooling. We use the pooled connection string for API routes (many short-lived connections) and direct connection for cron workers (fewer, long-lived). Row-level security: RLS policies on all user-owned tables ensure a user can only SELECT/UPDATE/DELETE their own rows. This is both security AND a performance filter — queries are automatically scoped. Data lifecycle management Job archival: Jobs not seen by cron for 14+ days are marked is_active = false. After 90 days, inactive jobs with zero applications are hard-deleted. Jobs with applications are kept permanently for user history. Resume recipe archival: Recipes for applications in rejected/no_response status for 60+ days are compressed to a summary (1KB) and is_archived = true. Full recipe can be regenerated from profile + JD if user requests. Weekly usage reset: Cron function runs every Monday at midnight UTC. Inserts new weekly_usage row for each active user. Old rows kept for analytics. 11. Lazy loading and code splitting Karmio loads only what the user needs, when they need it. This keeps initial page load under 200KB and time-to-interactive under 2 seconds. Route-level code splitting (automatic) Next.js App Router automatically splits code per route. When user navigates to /jobs/feed, only the job feed page bundle loads. The resume editor, networking module, and interview prep code are not loaded until visited. Each rate limit check is a single SQL query: // lib/rate-limit/limiter.ts export async function checkRateLimit( userId: string, action: string, limit: number, windowMs: number ): Promise<{ allowed: boolean; remaining: number; resetAt: Date }> { const windowStart = new Date(Date.now() - windowMs); const { count } = await supabase .from('rate_limit_log') .select('id', { count: 'exact' }) .eq('user_id', userId) .eq('action', action) .gte('created_at', windowStart.toISOString()); return { allowed: count < limit, remaining: Math.max(0, limit - count), ... }; } Rate limit response headers Every API response includes rate limit information in headers: X-RateLimit-Limit: 30 X-RateLimit-Remaining: 24 X-RateLimit-Reset: 1711123200 When limit is exceeded, return 429 Too Many Requests with a clear error message and the time until reset. AI cost protection Beyond rate limits, we have a global AI spend circuit breaker: Per-user daily AI budget: Free = $0.05, Popular = $0.50, Pro = $1.00. If a user somehow burns through this (automated abuse), AI endpoints return a friendly message. Global monthly budget alarm: If total AI spend exceeds 80% of projected budget, alert the admin. At 95%, automatically downgrade AI model from Haiku to a smaller model. Abuse detection: If a single user generates 50+ resumes in an hour (impossible in normal usage), auto-flag the account for review. 13. Security architecture Authentication and authorization Supabase Auth: Handles all auth flows (email/password, Google OAuth, Apple OAuth). JWTs are HttpOnly cookies, not stored in localStorage. Refresh tokens rotate automatically. Row-Level Security (RLS): Every user-owned table has RLS policies. Even if an API bug exposes a query, the database enforces that users only see their own data. Role-based access: Three roles: user (default), admin, system. Admin endpoints check role before executing. System role is for cron workers and webhooks only. Data protection Encryption at rest: Supabase encrypts all data at rest using AES-256. We do not need to manage encryption keys. Encryption in transit: All connections use TLS 1.3. Vercel handles SSL termination for the frontend. Supabase handles it for database connections. Sensitive field hashing: Passwords are hashed by Supabase Auth (bcrypt). We never store or see plain-text passwords. PII handling: User resumes are stored as recipes (structured JSON), not as files containing PII. When a user deletes their account, all data is hard-deleted within 30 days. API security CSRF protection: Next.js API routes are same-origin by default. We add CSRF tokens for state-changing operations. Input validation: Every API endpoint validates input using Zod schemas. Invalid data is rejected with a 400 before any business logic runs. SQL injection: Supabase client uses parameterized queries. We never construct raw SQL strings from user input. XSS prevention: React escapes all rendered content by default. User-generated content (notes, messages) is sanitized with DOMPurify before storage. Stripe webhook verification: All Stripe webhooks are verified using the webhook signing secret. Unverified requests are rejected with 401. Environment variables # Public (exposed to browser) NEXT_PUBLIC_SUPABASE_URL=https://xxx.supabase.co NEXT_PUBLIC_SUPABASE_ANON_KEY=eyJ...
